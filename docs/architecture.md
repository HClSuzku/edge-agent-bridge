# 架构

## 一句话

Cloudflare Durable Object 常驻接管消息拉取与排队，instabox 上的执行器随时可丢；盒子休眠时 DO 继续收消息并负责叫醒它。

## 为什么需要这一层

把 agent 跑在按秒计费的沙箱里，难点从来不是"怎么跑"，而是三件事：

1. 沙箱会休眠，休眠期间谁收消息？
2. 消息平台（微信 iLink 之类）的拉取接口是**单消费者**语义，谁先拉谁拿走、不可重放。盒子自己拉、平台代理兜底拉，必然丢消息。
3. 沙箱是"可丢"的：进程会被杀、盘会掉、唤醒要几十秒。业务状态不能只存在它上面。

所以把"收"和"做"拆开：DO 负责收和排队（永不睡），盒子负责做（随时可睡）。游标只归 DO 一家，任何人不得并发拉取。

## 组件

```
微信用户
   │  普通微信消息
   ▼
iLink（微信官方机器人通道）
   │  getupdates 长轮询（单消费者）
   ▼
Cloudflare Worker ── 鉴权 / 唤醒 / 入队 / 查询（无状态）
   ├── Durable Object: WxRelay   ← 游标唯一持有者，alarm 自续期
   └── Durable Object: JobQueue  ← 通用任务队列（可选）
   ▲
   │  /wx/claim、/wx/ack、/wx/hb
   ▼
instabox 沙箱（可休眠）
   ├── weixin_relay.py   认领 → 交给 runtime → 回执
   └── agent.py          通用任务执行器（可选）
```

## 职责边界

| 组件 | 负责 | 不负责 |
| --- | --- | --- |
| Worker（入口） | 鉴权、路由、唤醒接口 | 存状态、发消息 |
| WxRelay (DO) | 拉取 iLink、队列、租约、唤醒判断 | 跑 agent |
| JobQueue (DO) | 通用任务入队/认领/回执 | 碰微信游标 |
| 盒子 | 认领消息、跑 agent、回执 | 拉 iLink、管队列 |

## WxRelay 的状态机

消息在队列里只有四种状态：

- `queued` — 已入队，等盒子来认领
- `claimed` — 已被某个 client_id 拿走，带租约
- `done` — 已回执，按 message_id 去重 24 小时
- `parked` — 重试 3 次或滞留 10 分钟，移出主队列留档

认领时写入 `_owner`（盒子的 client_id）。同 owner 再次认领，即使租约没到期也直接重发内容——这是"服务端已租出、但响应在网络里丢了"的唯一恢复路径，也是把租约从主路径降级为兜底的关键。

## 定时驱动

WxRelay 用 DO alarm 自我驱动，不依赖外部 cron、不依赖盒子心跳：

```
alarm 醒来 → 拉一次 iLink（9 秒长轮询）→ 有新消息就入队
           → 心跳超 90 秒就调 instabox 唤醒
           → setAlarm(now + 10s) 无条件续期
```

周期 10 秒、每次轮询 9 秒，活跃度 90%。延迟盲区最大 1 秒，加盒子侧 3 秒认领间隔，正常情况下 1～4 秒出回复。

关键：alarm 必须**无条件**自续期。早期版本的续期写在心跳分支里，盒子一睡死，闹钟就不续了，整条链路静默停摆。

## 唤醒判断

DO 记录盒子最后一次心跳时间。拉到新消息时：

- `now - lastHeartbeat > 90s` → 认为睡着 → 调 instabox 的 start 接口
- 否则 → 认为醒着 → 不调（唤醒接口本身也是一次外部 API 调用，省掉）

90 秒这个窗口对应盒子 20 秒一次的心跳，留了三倍余量。副作用是：盒子刚挂起时最后心跳仍在窗口内，此时发消息不会触发唤醒，要等心跳过线——实测约 1～2 分钟。

## 时序：盒子睡着时来一条消息

```
t+0s     用户发消息 → iLink 暂存
t+0~10s  DO alarm 拉取 → 入队 → 心跳超时 → 调 start
t+10~40s 沙箱从挂起到 ready（实测冷启动主要耗在这里）
t+醒后   盒子启动 adapter → 每 3 秒认领一次
t+认领   拿到消息 → 交给 runtime → 回执 → 经 iLink 发回
```

整段实测：首条消息从发出到回复常在一分钟内，盒子已醒时 1～4 秒。

## 幂等设计

| 场景 | 行为 |
| --- | --- |
| 认领响应丢了 | 同一 client_id 下轮重试，DO 直接重发内容（秒级） |
| 盒子进程重启 | client_id 变了，等租约过期（≤60 秒）后重投 |
| 盒子整机睡死 | DO 照常入队，唤醒后按上面两条走 |
| 重复投递 | 回执后按 message_id 记 done，24 小时内不再投 |

租约因此只兜底"owner 换了"这一种情况，正常故障恢复是秒级而非等 60 秒。
