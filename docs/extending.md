# 扩展

这一层的价值在于"入口可换、执行器可换"。下面三条是常见方向，都不需要改 DO 的核心逻辑。

## 1. 加一个入口（飞书 / Telegram）

微信的接入是 iLink 拉取 → WxRelay 入队 → 盒子认领。换平台时只有两处不同：

- **拉取方式**：飞书长连接事件、Telegram `getUpdates` 是推/拉不同的模型
- **发送方式**：各自的 send API

做法：复制一个 `Ingress` DO（如 `FeishuRelay`），只改三处——拉取、发送、去重键。队列结构、租约、`_owner` 幂等原样复用。

注意两个陷阱：

- 飞书事件回调要验签，且首次配置有 challenge 握手
- Telegram 的 `getUpdates` 同样是单消费者，游标只能有一家

若平台本身可推（webhook），优先用推送：能省掉整个轮询成本，机器不常醒也不怕丢消息。此时 Ingress 只做入队 + 唤醒，比本方案更便宜。

## 2. 换成别的执行器

adapter 与 runtime 之间只有一层薄协议：认领到消息 → 交给执行器 → 拿回文本 → 回执。想换 runtime（openclaw、pi、deepseek-harness、任意 CLI）只需要实现：

```
def handle(msg) -> str      # 输入消息文本，返回回复文本
```

`box/agent.py` 里有一份最小实现示例。要点：

- 执行器要有自己的超时（别让一条坏消息卡住整个循环）
- 回复要能分段（平台消息有长度上限），长文本先切再发
- 执行器崩溃不应该拖死 adapter：捕获异常，回执一条错误说明，让队列继续走

## 3. 多 agent / 多机器人

一个 WxRelay 实例 = 一个微信通道 = 一份活跃时长。多机器人时：

- 每个 bot 一个 DO 实例（用 `idFromName(botId)`）
- 别让多个 bot 共用一个 DO，会互相抢游标
- 盒子侧按 bot 分队列目录，避免串号

成本上，第二个 bot 基本等于把费用翻倍（活跃时长是主要开销）。如果只是给不同的人用同一个 agent，优先考虑"一个入口 + 路由到不同会话"，而不是多个入口。

## 4. 可选：任务队列（JobQueue）

`JobQueue` 是跟微信无关的通用队列，`/jobs` 投递、`/agent/next` 认领、`/agent/result` 回执。适合"跑一个长任务，稍后取结果"的场景。

它**不参与**微信链路。早期版本让它每 40 秒巡检唤醒盒子，结果和 WxRelay 抢游标（见 pitsfalls 第 8 条），现在已停用。要用就配独立的唤醒逻辑，别和微信共用心跳判断。

## 5. 加监控

最小可用监控只要三样：

- `/status` 的 `lastHeartbeat` 年龄（超过 90 秒说明盒子不在）
- 队列里 `queued` 数量（持续增长说明盒子没在认领）
- 消息从入队到回执的耗时（超过 10 秒说明有人在等租约）

三者都可以用一个外部脚本定时拉 `/status` 实现，不需要 DO 内部埋点。
